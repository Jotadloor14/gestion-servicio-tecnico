# 🛡️ Matriz de Mitigación OWASP Top 10:2025
### Proyecto Integrador: Sistema Control Real (Ecosistema de Servicio Técnico y Stock)
**Institución:** I.T.S. Humane | **PAO:** 2026-B1 | **Docente:** Ing. Julio Vásconez

A continuación se detalla el análisis del MVP contra los riesgos más críticos de las aplicaciones web, implementando los principios de Privilegio Mínimo, Defensa en Profundidad y Fallar Cerrado en el servidor local.

| Riesgo | ¿Aplica? | Dónde (Ruta / Archivo / Tabla) | Cómo podría explotarse (Vector de Ataque) | Solución Técnica Implementada / Planificada | Prioridad |  |
| :--- | :---: | :--- | :--- | :--- | :---: | :---: |
| **A01: Control de acceso roto** | **Sí** | `POST /api/auth/login/`<br>Vistas: `/personal/`, `/reportes/` | Escalación vertical: Un `tecnico` manipula la URL en el navegador o intercepta las peticiones para forzar el acceso a las vistas administrativas exclusivas de personal o reportes. | Se implementó el decorador perimetral de backend `@rol_requerido(roles_permitidos=['administrador'])` en `views.py`. Si el rol en sesión no coincide, el servidor interrumpe el hilo y **falla cerrado** con un HTTP `403 Forbidden`. | **Alta** |  |
| **A02: Configuración de seguridad incorrecta** | **Sí** | Archivo:<br>`config/settings.py` | Exposición de trazas: Dejar el entorno en modo desarrollo (`DEBUG = True`) en producción, permitiendo que un error 500 exponga la traza detallada del código (`Traceback`), credenciales a MySQL o el mapa de directorios de la laptop. | Se configuró de forma rígida `DEBUG = False` y se restringió la variable `ALLOWED_HOSTS = ['127.0.0.1']`. Los recursos estáticos se manejan en subdirectorios controlados desactivando el listado automático de carpetas. | **Alta** |  |
| **A03: Fallas en la cadena de suministro** | **Sí** | Archivo:<br>`requirements.txt` | Dependencias vulnerables: El uso de versiones desactualizadas del framework que posean vulnerabilidades críticas ya indexadas y descubiertas por la comunidad internacional. | **Auditoría Real Realizada:** Se ejecutó `pip-audit -r requirements.txt` detectando **8 vulnerabilidades conocidas en Django 5.1.15**. Mitigación: Se planifica congelar la cadena actualizando a **Django 5.2.17** o superior. | **Alta** |  |
| **A04: Fallas criptográficas** | **Sí** | Base de Datos:<br>Tabla `Usuario` en MySQL | Filtración de accesos: Almacenar las contraseñas de los empleados en texto plano o con algoritmos obsoletos (MD5/SHA1), permitiendo que un volcado o inyección de la base de datos exponga las claves. | Se delegó la seguridad de credenciales al motor nativo de Django, el cual aplica funciones hash criptográficas irreversibles **PBKDF2 combinadas con SHA-256** y un *salt* único y dinámico por cada registro. | **Alta** |  |
| **A05: Inyección** | **Sí** | `POST /api/auth/login/`<br>Formularios de la interfaz | Inyección SQL/XSS: Ingresar caracteres o sentencias maliciosas en las cajas de texto de búsqueda o login (ej: `' OR '1'='1`) para evadir los controles lógicos o alterar los registros de MySQL. | La captura de datos asíncronos se procesa de forma aislada vía objetos estructurados JSON con `json.loads(request.body)`. El ORM de Django parametriza automáticamente las consultas, separando datos de instrucciones. | **Alta** |  |
| **A06: Diseño inseguro** | **Sí** | Formulario:<br>`templates/dashboard_admin.html` | Abuso del flujo lógico: Un usuario malintencionado aprovecha la falta de lógica defensiva en el backend para registrar una nueva orden de servicio ingresando valores negativos en el campo de abonos contables. | Se implementó una validación perimetral rígida a nivel de servidor previa al guardado en la base de datos (`if abono < 0`), rechazando la transacción si viola las reglas lógicas y contables del taller. | **Media** |  |
| **A07: Fallas de autenticación** | **Sí** | Endpoint:<br>`/api/auth/login/` | Ataque de fuerza bruta: Ejecución de un script automatizado para probar miles de contraseñas por segundo contra la cuenta `admin` hasta adivinar el acceso por falta de restricciones. | Se unificaron las respuestas de denegación a un mensaje genérico `{'error': 'Credenciales inválidas'}` (HTTP 401) para neutralizar la enumeración de usuarios, y se requiere la cabecera obligatoria `X-CSRFToken`. | **Alta** |  |
| **A08: Fallas de integridad de datos** | **No** | *No aplica en el almacenamiento local* | Modificación de claims: Alterar los datos de identidad locales de un token desprotegido para elevar privilegios en la aplicación (riesgo típico al leer tokens JWT con `jwt.decode` sin verificar la firma digital). | **Justificación:** El sistema del taller no almacena tokens JWT en el almacenamiento del cliente para gestionar la navegación. La persistencia y validación del estado se administra en el servidor mediante el motor de sesiones nativas de Django. | **Baja** |  |
| **A09: Fallas de registro y alertas** | **Sí** | Terminal y Logs del Servidor | Sabotaje interno: Modificación no autorizada de inventario o ingreso a rutas administrativas por parte de un técnico sin dejar un rastro forense o registro de auditoría del evento. | El backend de Django inmortaliza automáticamente en los logs de la terminal el método HTTP, la marca de tiempo exacta, la IP y el código de estatus resultante de cada petición (ej: `GET /personal/ 403`), prohibiendo imprimir claves. | **Media** |  |
| **A10: Manejo inadecuado de excepciones** | **Sí** | Bloque `try/except` en `views.py` | Fuga de información: Forzar un desplome del backend (Error 500) enviando objetos JSON malformados o corruptos para provocar la exposición involuntaria de líneas de código o variables de desarrollo. | Se envolvieron los endpoints críticos en estructuras de control `try/except json.JSONDecodeError`. Ante una petición corrupta, el backend aplica el principio de **fallar cerrado**, enviando un estado HTTP 400 genérico. | **Media** |  |
